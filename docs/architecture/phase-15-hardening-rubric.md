# Phase 15+ Hardening Rubric

## Purpose

This document is the evidence contract for the next CityEvents hardening track.
It prevents drift while implementing:

- Kubernetes live evidence
- failure testing
- OpenTelemetry and observability upgrades
- Redis-backed distributed rate limiting
- load-test evidence
- frontend hardening

Each item is only resume-safe after the matching code, tests, scripts, and
recorded evidence exist.

Heavy evidence is GitHub Actions-only. Do not run Kubernetes live smoke,
Kubernetes live failure mutation, or gateway load evidence from the local
workstation. The runner policy is recorded in
`docs/testing/heavy-evidence-runner-policy.md`.

## Phase 15: Kubernetes Live Evidence

### Required Functionality

- Repair or recreate a broken Minikube profile only inside GitHub Actions.
- Treat Minikube smoke as host-level evidence; do not run it silently or as part
  of normal local verification.
- Block the live smoke outside GitHub Actions.
- Run a GitHub Actions Kubernetes smoke with the existing `deploy/kubernetes/local`
  overlay.
- Apply migrations inside the Kubernetes Postgres pod.
- Verify gateway health, admin login, organizer promotion, event creation,
  attendee join, metrics, and one selected app pod deletion/replacement.
- Record all evidence under `tmp/k8s-live-smoke/<timestamp>/`.

### Done Evidence

- `./scripts/verify-phase-14.sh` passes.
- `./scripts/verify-phase-15.sh` passes and proves the smoke script has no
  host process-killing cleanup.
- The manual GitHub Actions `Heavy Evidence` workflow passes the Kubernetes
  live smoke job.
- Evidence contains `summary.md`, `deployments.txt`, `pods-after-start.txt`,
  `pods-after-failure.txt`, `deleted-pod.txt`, and `metrics.txt`.
- `summary.md` states the cluster context, exact command, and limitation that
  local backing services are single-instance.

### Quantitative Gate

- All 10 app workloads report available.
- Gateway `/readyz` passes before and after pod deletion.
- The smoke workflow creates one event and one confirmed join.
- No host process is killed except the port-forward child process started by
  the same script.

### Claim Boundary

Allowed only after live success:

```text
Smoke-tested the CityEvents service set in local Kubernetes and verified app pod replacement.
```

Still not allowed:

```text
Production high availability.
```

## Phase 16: Failure Testing

### Required Functionality

- Add repeatable failure tests for:
  - API pod deletion during readiness checks
  - worker restart during queued message processing
  - RabbitMQ outage during outbox relay publishing
  - Redis outage during feed reads and token/rate-limit fast paths
  - Postgres unavailable behavior
- Add RabbitMQ reconnect behavior for the outbox relay and consumers so broker
  restart can be tested without manually restarting app processes.
- Preserve core correctness after each failure scenario.
- Block live failure mutation outside GitHub Actions.

### Done Evidence

- Failure scripts write summaries under `tmp/failure-tests/<timestamp>/`.
- Live failure evidence is generated by GitHub Actions, not the local
  workstation.
- The manual `Heavy Evidence` workflow uploads `dependency-failure-evidence`
  when Redis/RabbitMQ scenarios run.
- At least one successful run is documented in `docs/testing/failure-testing.md`.
- No failure test silently upgrades the HA claim.

### Quantitative Gate

- RabbitMQ/outbox test proves pending outbox rows are retried after broker
  recovery and reach the feed projection after reconnect.
- Redis outage test proves reads fall back to Postgres or fail safely without
  corrupting state.
- Redis outage test proves configured rate limiting behavior is explicit
  fail-open or fail-closed.
- Join correctness remains `confirmed <= capacity`.

### Claim Boundary

Allowed:

```text
Added GitHub-Actions-only failure evidence tooling and RabbitMQ reconnect loops for broker/cache/service recovery paths.
```

Not allowed until dependency HA exists:

```text
Failure-tested production high availability.
```

## Phase 17: Observability Upgrade

### Required Functionality

- Add OpenTelemetry trace configuration.
- Add HTTP spans with route, method, status, service, and correlation ID.
- Propagate W3C trace context across HTTP requests.
- Propagate trace metadata in RabbitMQ message headers.
- Provide local collector and dashboard configuration files.
- Keep existing `/metrics` Prometheus text endpoint.

### Done Evidence

- Unit tests verify trace headers are accepted and propagated.
- RabbitMQ publishing includes trace headers when context is present.
- Docs explain how to run a collector and where traces/metrics appear.

### Quantitative Gate

- One join workflow can be traced through at least:
  - gateway HTTP request
  - event-registration HTTP request
  - outbox publish
  - feed or notification consumer handling
- Metrics still expose request counter, request histogram, rate-limit counter,
  outbox counter, and consumer counter.

### Claim Boundary

Allowed:

```text
Instrumented services with correlation IDs, Prometheus metrics, and OpenTelemetry trace propagation.
```

Not allowed until a collector/dashboard is run and recorded:

```text
Production observability stack.
```

## Phase 18: Redis Distributed Rate Limiting

### Required Functionality

- Replace or supplement the per-process limiter with a Redis-backed fixed-window
  limiter.
- Keep memory limiter as a local fallback.
- Make fail-open/fail-closed behavior explicit through configuration.
- Apply the same scope model: auth, mutation, read.
- Keep health, readiness, metrics, root, and CORS preflight exempt.

### Done Evidence

- Unit tests cover Redis limiter behavior through a fake store.
- Config tests cover backend selection and fail-open mode.
- Local integration/load test proves `429` behavior still works.
- Docs explain security tradeoffs of fail-open versus fail-closed.

### Quantitative Gate

- With limit `2`, the third same-key request returns `429`.
- `Retry-After` is set.
- Redis store error increments a metric and follows configured fail behavior.

### Claim Boundary

Allowed:

```text
Added Redis-backed shared rate limiting with documented fail-open/fail-closed tradeoffs.
```

Not allowed:

```text
Edge-grade DDoS protection.
```

## Phase 19: Load Evidence

### Required Functionality

- Extend load testing to capture latency percentiles, request counts, status
  counts, throughput, CPU/memory snapshots, and dependency state where available.
- Run the manual GitHub Actions matrix at 40, 80, and 160 users.
- Block load evidence outside GitHub Actions.
- Keep correctness gates for capacity and waitlist invariants.

### Done Evidence

- `tmp/load-test-local/<run-id>/summary.md` includes p50, p95, p99, max latency,
  join throughput, success rate, and dependency snapshots when available.
- Load evidence artifacts are uploaded from the manual GitHub Actions
  `Heavy Evidence` workflow as `load-evidence-small-40u`,
  `load-evidence-medium-80u`, and `load-evidence-stress-160u`.
- `docs/testing/load-testing.md` records the latest successful run.

### Quantitative Gate

- Join success rate is 100% for the configured local run.
- `confirmed == min(users, capacity)`.
- `waitlisted == users - confirmed`.
- Feed projection reaches the expected count within the configured timeout.

### Claim Boundary

Allowed:

```text
Added repeatable GitHub Actions load evidence for correctness, latency, and dependency snapshots under concurrent joins.
```

Not allowed:

```text
Production high throughput.
```

## Phase 20: Frontend Hardening

### Required Functionality

- Preserve the existing customer-facing discovery model.
- Improve maintainability with a clearer module/component split.
- Keep runtime API base configuration.
- Preserve memory-only access-token behavior and CSRF refresh/logout handling.
- Add browser E2E coverage for publish, join, cancel, and auth state.
- Keep visual design aligned with `PRODUCT.md` and `DESIGN.md`.

### Done Evidence

- `npm run verify` passes.
- `npm run e2e` passes.
- Browser screenshots are reviewed for desktop and mobile.
- The UI has no text overflow, obvious contrast problems, or disjoint theme
  treatment.

### Quantitative Gate

- Primary tap targets are at least 44px high.
- The first viewport contains discovery/search, one strong event, and category
  entry points on desktop.
- The publish -> detail -> join path completes in browser E2E.

### Claim Boundary

Allowed:

```text
Hardened the frontend workflow with maintainable modules and browser E2E coverage.
```

Not allowed:

```text
Production frontend performance benchmark.
```

## Anti-Drift Rule

Do not start the next phase claim until the current phase has:

- implementation
- tests or scripts
- docs
- evidence output
- claim boundary update
